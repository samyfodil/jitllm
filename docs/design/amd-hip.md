# A native AMD backend: HIP through goffi, kernels from the IR

**Status: the design. The binding, the lowering and the device follow it.**

The requirement, stated by the user: a native AMD backend reached through goffi
(dlopen `libamdhip64` and `libamd_comgr`, no cgo), whose kernels are GENERATED by
jitllm's own IR at run time for the GPU in front of it -- a fourth lowering beside
PTX, SPIR-V and MSL -- with comgr used only to turn what jitllm emits into a code
object for `hipModuleLoadData`. No HIP C++ source, no hipcc, no hiprtc, no
precompiled kernels. Without ROCm, AMD hardware keeps running through Vulkan,
unchanged.

Two more, stated by the user and binding:

1. **No external command.** Nothing execs hipcc, clang, ld.lld, rocminfo,
   rocm-smi, amdgpu-arch or anything else. Code objects come only from comgr's
   library API (`amd_comgr_do_action`); devices and their properties only from
   HIP calls (`hipGetDeviceCount`, `hipGetDevicePropertiesR0600` for
   `gcnArchName`, `hipDeviceGetAttribute`, `hipDeviceGetUuid`). Gate:
   `srcgate`'s production-import sweep refuses `os/exec` in any non-test file
   outside `cmd/` and `dev/`, and `hip.TestNoExternalCommands` holds the
   package itself.
2. **ROCm is discovered and loaded at run time**, as `jit/gpu/cuda` finds
   libcuda. Sonames first (`libamdhip64.so.7`, `.so.6`, `.so`;
   `libamd_comgr.so.3`, `.so.2`, `.so`), through the loader's own search path,
   then `/opt/rocm/lib`, every `/opt/rocm-*/lib` newest version first, and
   `/usr/lib/x86_64-linux-gnu`. An explicit directory is `hip.Config.Path`,
   reached through `tier.WithROCm` and filled by `cmd/jitllm` and `jitllmd`
   from `JITLLM_ROCM` (the libraries read no environment). A named directory
   is the ONLY one tried. Absent or unloadable ROCm is zero HIP devices and
   never an error; the build stays `CGO_ENABLED=0`, and one binary runs with or
   without ROCm. Gate: `hip.TestBogusROCmIsNoDevices`.

This is a fourth BACKEND behind the existing `backend.Device`, not a new
abstraction: AGENTS.md's "do not add a fourth abstraction in advance of a second
implementation" is about layers, and this adds none.

## The lowering target: LLVM IR text, handed to comgr

There were two ways to hand comgr something to turn into a code object:

| | AMDGPU assembly (`ASSEMBLE_SOURCE_TO_RELOCATABLE`) | LLVM IR (`COMPILE_SOURCE_TO_BC` with `LANGUAGE_LLVM_IR`, `CODEGEN_BC_TO_RELOCATABLE`) |
|---|---|---|
| who allocates registers | jitllm: a register allocator, s_waitcnt insertion, the hazard rules of every generation | the AMDGPU code generator |
| wave32 / wave64 | two instruction streams (VCC is 32 or 64 bits, EXEC likewise) | one text; the target's wave size is the code generator's |
| a new gfx generation | new encodings and hazards | a new target name |
| what stays jitllm's | everything | the kernel's structure: the tile, the loop nest, the loads, the reductions |

**LLVM IR, as text.** It is what PTX is to ptxas: a virtual-register assembly
the vendor's back end owns instruction selection, register allocation and
scheduling for -- exactly the division `jit/gpu/ir`'s package comment draws ("the
device driver owns instruction selection, register allocation and scheduling on
every target"). Writing GCN assembly would mean writing that back end, four
times over (gfx9, gfx10, gfx11, gfx12 differ in encodings, wave size and hazards).
What the user asked to stay ours does: the IR is jitllm's, the lowering is one
forward walk like `ptx.Lower`, and its output is text a test can read and a golden
can pin. comgr parses the text in process (`COMPILE_SOURCE_TO_BC` with
`AMD_COMGR_LANGUAGE_LLVM_IR`, run at -O3, which also promotes nothing because the
lowering emits SSA), generates code (`CODEGEN_BC_TO_RELOCATABLE`) and links the
code object (`LINK_RELOCATABLE_TO_EXECUTABLE`), all through `amd_comgr_do_action`.
Verified on comgr 3.0 (ROCm 6.4.1): textual IR is accepted by all three actions
for all four targets.

Why not SPIR-V into comgr (`AMD_COMGR_DATA_KIND_SPIRV`, ROCm 6.4)? It would reuse
`spirv.Emit`, but comgr's SPIR-V path is a translator into the same LLVM IR, newer
and less exercised than its LLVM IR input, and the Vulkan SPIR-V jitllm emits is a
shader-environment module (Logical addressing, a push-constant group base), not the
OpenCL-environment kernel the translator reads. A separate lowering is the smaller
risk and costs one file.

## The IR's ops on AMDGPU

The lowering mirrors `ptx.Lower` op for op. What is not a transcription:

- **Address spaces.** Parameters are `ptr addrspace(1)` (global); `OpShared` is an
  `internal addrspace(3)` array (LDS) declared at module scope, its size fixed at
  emission as on every target; private memory (`addrspace(5)`) is never used,
  and a kernel whose code object reports scratch is a gate failure.
- **Indexing.** An element index is u32 widened to i64 before the offset is added,
  which is `mad.wide.u32`'s arithmetic.
- **Integer shifts by 32 or more** are poison in LLVM and 0 in PTX's `shl.b32`/
  `shr.u32`. The lowering emits the PTX semantics (a select on `n < 32`, folded
  away when `n` is a constant), so no kernel depends on which back end it reached.
- **`OpCvtI32`** is `llvm.fptosi.sat`, which is PTX's `cvt.rzi.s32.f32`
  (saturating, NaN to 0); a bare `fptosi` is poison out of range.
- **`OpExp`** is `exp2(x * log2 e)`, the same approximation PTX takes; `OpSqrt` is
  `llvm.sqrt.f32`, correctly rounded on AMDGPU as `sqrt.rn` is.
- **`OpMin`/`OpMax` on f32** are `llvm.minnum`/`llvm.maxnum`: PTX's `min.f32`
  returns the non-NaN operand, and so do these.
- **`OpDot4`** is `llvm.amdgcn.sdot4` where the target has `v_dot4_i32_i8`
  (gfx90a, gfx942: dot1-insts) and `llvm.amdgcn.sudot4` with both operands
  signed where it has `v_dot4_i32_iu8` instead (gfx11, gfx12, which dropped the
  first). The choice is a per-target table in `amdgpu.Target`, checked by the
  offline gate assembling it for every target.
- **`OpBarrier`** is HIP's `__syncthreads`: a workgroup release fence,
  `llvm.amdgcn.s.barrier`, a workgroup acquire fence. The fences are what order
  LDS (and global) accesses across the barrier under the AMDGPU memory model; the
  bare `s_barrier` does not.
- **Loops** are a guarded do-while: the guard skips a zero trip count, the header
  carries `phi` nodes for every `OpPhi`, and the exit carries LCSSA `phi`s for
  every value of the loop used after it, so a zero-trip `LoopN` yields the phi's
  init as `ptx.Lower`'s register would.

### Subgroups: wave64 (CDNA) and wave32 (RDNA)

The IR's cross-lane op, `OpShuffleXor`, is defined over an aligned block of 32
lanes with a mask in [1,31] (`ir.SubgroupLanes`). It lowers to
`llvm.amdgcn.ds.bpermute` with the source lane `(lane ^ mask)`, `lane` from
`mbcnt`. On a 32-wide wave that is the whole wave. On a 64-wide wave, a mask
below 32 cannot leave the lane's own aligned half, so a 32-lane butterfly is the
same computation in both halves independently -- the answer the IR defines.

So the backend can promise `GuaranteedLanes(32)` on BOTH wave sizes, and that
promise is not an observation (RULE 12ah): it follows from the mask bound,
which `ir.Validate` enforces, and from the code generator taking the wave size
from the target, which the code object's `.wavefront_size` states and the
backend reads (a kernel generated at a width the device does not run at is
refused at load). A width other than 32 is refused.

`ds_bpermute` reads a lane's value as it stands; a lane that is inactive gives 0.
Structured control flow reconverges at every loop exit, so every shuffle in an IR
kernel is reached by the whole wave, as `shfl.sync` requires on PTX.

### The matrix paths: MFMA and WMMA

`ir.OpMMA` is NVIDIA's fragment contract: a 32-lane warp with a documented
per-lane layout. Neither AMD instruction has that layout -- MFMA (CDNA gfx90a,
gfx942) spreads a tile over 64 lanes with accumulators in AGPRs, WMMA (RDNA3
gfx11, RDNA4 gfx12) over 32 lanes with operands replicated across the two
16-lane halves on gfx11 and not on gfx12. So the lowering refuses `OpMMA`, as
SPIR-V and MSL do, and the tier selects the scalar and dot4 kernels the other
non-PTX backends run.

The collective tile ops (`OpTileLoad`/`OpTileMMA`/`OpTileStore`) are the right
door: the layout is the lowering's to choose, which is what both AMD instructions
need. They are refused for now. The work, in order: WMMA f16->f32 16x16x16 on
gfx11/gfx12 (`llvm.amdgcn.wmma.f32.16x16x16.f16`, with gfx11's operand
replication), int8 WMMA (`wmma.i32.16x16x16.iu8`), then MFMA on gfx90a/gfx942
(`mfma.f32.32x32x8f16`, `mfma.i32.32x32x16.i8` on gfx942), each behind the
cooperative-matrix capability list a backend already reports, and each gated
against the scalar kernel on a card.

## Memory model, kernel descriptor and arguments

- Every kernel is `amdgpu_kernel` with `"amdgpu-flat-work-group-size"="G,G"` and
  `"uniform-work-group-size"="true"`: the launch width IS the declared group
  (`backend.checkWidth`), so the code generator may assume it, and `OpNTID` is
  that constant, as MSL lowers it.
- The kernel descriptor (`.kd`) is the linker's; the code object metadata
  (`amdhsa.kernels`) is read back through comgr for each kernel's SGPR, VGPR,
  AGPR, LDS and scratch usage and wave size (`hip.KernelMeta`).
- Arguments are the parameters' device addresses in declaration order, eight bytes
  each, passed through `hipModuleLaunchKernel`'s `kernelParams` -- the same shape
  as `cuLaunchKernel`.
- Cross-workgroup ordering is between launches only: consecutive launches on one
  stream are ordered, and the IR has no atomics.

## Device identity: one device, one identity

`hipDeviceGetUuid` on AMD answers the KFD's unique id ("GPU-" and hex), which no
Vulkan driver reports, so it cannot say that `hip:0` and `vulkan:0` are one card.
AMD's Vulkan driver (RADV) builds its `deviceUUID` from the PCI location, four
little-endian u32 of domain, bus, device and function (mesa,
`ac_compute_device_uuid`). The HIP backend's `Identity` is that same sixteen bytes
built from `hipDeviceAttributePciDomainID`/`PciBusId`/`PciDeviceId`, function 0 (a
GPU is function 0, and HIP exposes no function). Vulkan's side is unchanged. A
location the runtime will not give is an unknown identity, which leaves the two
views distinct: the safe direction, since a false merge deletes a card and a
missed one double-counts it until the caller names a device. The KFD id is still
read and reported.

## Unified memory on APUs

`hipDeviceAttributeIntegrated` says the device's memory is the host's (an APU:
Strix Halo, MI300A). `UnifiedMemory()` reports it, with the one contract every
backend has: SUBTRACT, DO NOT ADD.

## The default set's order: CUDA > Metal > HIP > Vulkan

`backend.APIRank` orders backends for ONE physical device seen through several.
An AMD card is never also a CUDA or a Metal device on Linux, so only HIP against
Vulkan is ever decided, and HIP ranks above Vulkan: it is AMD's own compute stack,
it allocates device memory without a host-visible staging buffer, and it is the
path that will take the matrix units. That is a decision, not a measurement: once
the device gates pass on a card, the same-card A/B (RULE 1, `vs-llamacpp.sh`'s
harness, jitllm `-devices hip` against jitllm `-devices vulkan`, decode and
prefill) decides whether it stands. Until then a caller who wants Vulkan on that
card names it (`-devices vulkan`).

`-devices` spells the backend `hip` (also `rocm`, `amdgcn`), and its selector is
an ordinal, as CUDA's.

## The comgr dependency

ROCm present (libamdhip64 and libamd_comgr both load, `hipInit` succeeds, at
least one device): HIP devices. Anything else: none, and AMD hardware is reached
through Vulkan exactly as before. comgr alone (no HIP, no GPU) is enough to
generate code objects, which is what the offline gates use: comgr assembles for
any gfx target with no device present.

## Gates

Offline, on any Linux box with comgr reachable (`JITLLM_ROCM` names a directory;
the packages extract without root, see "Running the gates"):

- `amdgpu.TestLowersForEveryTarget` (`jit/gpu/lowertest`): every kernel in
  `lowertest`'s inventory -- the model gates' shapes -- lowers, passes
  `ir.Validate`'s RULE 13 invariants, compiles to a code object for gfx90a,
  gfx942, gfx1100 and gfx1201, and its metadata says no scratch and no spill,
  the wave size the target runs, and LDS equal to the shared arrays declared.
- `amdgpu.TestRefusesWhatItCannotLower`: OpMMA, the tile ops and nothing else.
- Lowering unit tests that read the text: shift semantics, saturating convert,
  the dot4 intrinsic per target, the barrier's fences, zero-trip loops.
- `hip.TestBogusROCmIsNoDevices`, `hip.TestNoExternalCommands`,
  `hip.TestVulkanUUIDIsRADVs`, the version ordering of `/opt/rocm-*`.

On a card (skip by name without one: "NO AMD DEVICE: ... did not run"):
`backend`'s kernel gates against the oracle run on every device `backend.Open`
returns, so the HIP device joins them with no new test; plus
`backend.TestHIPDeviceRunsTheIR` and the model gates with `-devices hip`.

## Running the gates on a rented card

Two cards: one CDNA (MI300X gfx942, or MI250X gfx90a) and one RDNA3/RDNA4
(RX 7900 XTX gfx1100, or RX 9070 XT gfx1201), each with ROCm 6.4 or later
installed (`/opt/rocm`). From the repo root on the rented box:

    ./scripts/hip-gates.sh

which runs, under `scripts/cap`, the offline gates, `jit/gpu/backend`'s kernel
gates with `-run` over every oracle comparison, and the model gates
(`TestEveryModelRunsGenerated`, `TestGreedyMatchesLlamaCpp`,
`TestBatchMatchesForward`, `TestDecodeDoesNotAllocate`, the relocation and paging
gates) with the device pinned to `hip`, and fails if any HIP gate printed
"NO AMD DEVICE".
